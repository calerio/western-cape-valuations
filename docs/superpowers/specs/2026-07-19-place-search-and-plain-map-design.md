# Place search + boundary highlight + plain "Map" view — design

**Date:** 2026-07-19 · **Status:** shipped
**Files:** `assets/places.js` (new), `assets/map.js`, `assets/tokens.css`, `map.html`,
`plain.html` (new), `data/geo/places.json` (generated by data repo `extract/export_places.py`).
Contract: `DATA_CONTRACT.md` §14–§15.

## What

1. An Apple-Maps-style glass search box on both map views: type any Western Cape town or
   suburb, fly there, and see its real boundary as a translucent highlight (the Google-Maps
   "suburb polygon" idiom).
2. A third view — plain vector map (`plain.html`) — alongside Explore and Satellite, with the
   same live parcels, click-to-valuation and wards.

## Key decisions (and why)

- **Boundary source: Stats SA Census 2011 place-name boundaries** served by the WC Government
  GIS (`StatsSA_CensusBoundaries` MapServer, layers 3 = Main Places / 1 = Subplaces; 348 + 1,578
  WC features). Chosen because it is *official published open data on the exact host the site
  already trusts for the cadastre*, with verified CORS to the site origin and `f=geojson`
  support. This retired the old "suburb borders aren't open data" assumption in `CLAUDE.md`.
- **Ship an index, live-fetch the polygons.** Pre-baking all polygons ≈ 3 MB; instead
  `places.json` carries only names + bboxes (~250 KB) and the polygon is fetched per selection
  (~10–200 KB), cached in-memory. Mirrors the §9 cadastre pattern, and makes failure asymmetric
  by design: fly-to always works (static bbox), only the highlight needs the live service.
- **Name cleaning at build time** (NU-drop, SP-fragment merge keyed on `(name, MP_CODE)`) —
  documented in §14 so a future refresh doesn't "fix" the merge as a bug.
- **Municipalities included in the index** for free: geometry from the committed
  `wc-municipalities.geojson`, no live fetch ever.
- **No on-map text label for the highlight.** The satellite inline style has no `glyphs` URL, so
  a symbol layer would silently render no text; rather than branch per basemap, the place name
  lives in the search input. (OpenFreeMap's style has glyphs, but shared code wins.)
- **MODE flag, not a second JS file.** `plain.html` sets `<body data-basemap="plain">`;
  `map.js` picks the style (`PLAIN_STYLE` = OpenFreeMap `liberty` — user-chosen over
  bright/positron) and skips `addBasemap()`. Everything else is identical code.
- **Layer ordering in plain mode:** all overlays insert before `firstSymbolLayerId(map)` so the
  vector basemap's labels stay readable above translucent fills. Satellite appends (no
  pre-existing layers).
- **Theming via CSS only:** the six `--map-*` overlay tokens moved from base `:root` onto the
  two theme pins (`[data-theme="dark"]` white-on-imagery / `[data-theme="light"]`
  ink-on-vector). `cssVar()` reads in JS are unchanged — the page's theme pin does the work.
- **Search UI:** `.platter` glass combobox below the brand platter (left stack: brand → search →
  ward chip; top-center would collide with the brand and view switcher on phones). 150 ms
  debounce, lazy index load on first focus, rank exact > prefix > substring with towns/munis
  before suburbs, full keyboard/ARIA combobox semantics. Diacritic-insensitive `norm()`
  (stronger than atlas.js's — "Wüpperthal", "Betty's Bay").
- **Place names are NOT translated** in `names{}` (only UI chrome strings were added to the
  catalog). `tn()` falls back to the literal name; StatsSA names are largely already
  local/Afrikaans spellings. Deliberate — don't add 1,900 entries.
- **Deep links** `#p/<typed-code>` restore a selection; the Satellite↔Map view links carry the
  hash so a selected place survives a view switch.

## Degrade matrix (verified)

| Failure | Behaviour |
|---|---|
| `places.json` 404 | search shows "Search unavailable right now"; map fine |
| Census service down | fly-to still works from bbox; hint chip; no highlight |
| OpenFreeMap down | plain view degrades like satellite tile gaps (map `error` handler); swap `PLAIN_STYLE` if persistent |
| No matches | honest "No matches" row |
